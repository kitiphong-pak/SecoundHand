# Open Redirect

บันทึกสำหรับศึกษา เขียนจากตอนทำหน้าล็อกอินแบบมี `?next=` ใน songtor ([src/lib/safeRedirect.ts](../../src/lib/safeRedirect.ts))

## สรุปสั้นๆ

**Open redirect** คือช่องโหว่ที่เว็บรับ URL ปลายทางมาจากผู้ใช้ แล้วพาคนไปที่นั่นโดยไม่ตรวจก่อน ผลคือใครก็สร้างลิงก์ที่ **ขึ้นต้นด้วยโดเมนของเรา** แต่ **พาไปจบที่เว็บของเขา** ได้

ตัวช่องโหว่เองไม่ได้ขโมยอะไรโดยตรง สิ่งที่มันขโมยคือ **ความน่าเชื่อถือของโดเมนเรา** แล้วเอาไปให้คนร้ายใช้ต่อ

- ชื่อทางการ: CWE-601 "URL Redirection to Untrusted Site"
- OWASP เรียกว่า "Unvalidated Redirects and Forwards"

---

## 1. มันเกิดขึ้นได้ยังไง

ฟีเจอร์ที่ทำให้เกิดช่องโหว่นี้เป็นฟีเจอร์ที่ **ผู้ใช้ต้องการจริงๆ** คือล็อกอินเสร็จแล้วพากลับไปหน้าที่ตั้งใจจะไป

```
คนกด "แชทกับผู้ขาย" → ยังไม่ได้ล็อกอิน
  → /login?next=/chat/abc
  → ล็อกอินเสร็จ → พากลับไป /chat/abc   ✅ นี่คือสิ่งที่อยากได้
```

ค่า `next` อยู่ใน URL และ **ใครก็แก้ได้** ถ้าโค้ดเขียนแบบนี้

```ts
// ❌ มีช่องโหว่
router.push(searchParams.get("next") ?? "/");
```

คนร้ายก็แค่เปลี่ยนเป็น

```
https://songtor.app/login?next=https://songtor-login.evil.com
```

## 2. สถานการณ์จริงกับ songtor

1. คนร้ายโพสต์ในกลุ่มซื้อขายมือสองเชียงใหม่ว่า "ขาย iPhone 13 ราคาถูก ดูรูปที่นี่" แล้วแปะลิงก์ด้านบน
2. คนเห็นลิงก์ขึ้นต้นด้วย `songtor.app` ซึ่งเป็นเว็บจริง จึงกดเข้าไป
3. เจอหน้าล็อกอินของ songtor **ของจริง** ล็อกอินด้วยรหัสจริง ตรงนี้ยังปลอดภัยอยู่
4. ล็อกอินเสร็จ ระบบพาไป `songtor-login.evil.com` ซึ่งทำหน้าตาเหมือน songtor ทุกอย่าง และขึ้นว่า "เซสชันหมดอายุ กรุณาเข้าสู่ระบบอีกครั้ง"
5. คนส่วนใหญ่ไม่ทันดู address bar เพราะเพิ่งอยู่บนเว็บจริงเมื่อวินาทีก่อน **เลยกรอกรหัสซ้ำ รหัสจึงตกไปอยู่กับคนร้าย**

จุดที่ทำให้แนบเนียนคือ **ทุกอย่างที่เหยื่อตรวจสอบได้ด้วยตาล้วนเป็นของจริง** ทั้งลิงก์ที่เห็นก่อนกด และหน้าล็อกอินแรกที่เจอ

## 3. ทำไมอันตรายกว่าที่คิด

| ใช้ทำอะไร | อธิบาย |
|---|---|
| **Phishing** | แบบในข้อ 2 ยืมความน่าเชื่อถือของโดเมนเรามาใช้ |
| **หลบตัวกรองลิงก์** | ระบบกรองลิงก์อันตรายบางตัว (อีเมล แชท แพลตฟอร์มโซเชียล) ดูแค่โดเมนของลิงก์ ลิงก์ที่ขึ้นต้นด้วยโดเมนที่ดูปลอดภัยจึงอาจหลุดผ่านไปได้ |
| **ขโมย token ของ OAuth** | ระบบ "Login with ..." ส่ง code หรือ token กลับไปที่ `redirect_uri` ซึ่งต้องอยู่ในรายชื่อที่อนุญาตไว้ ถ้าโดเมนที่อนุญาตมี open redirect อยู่ คนร้ายจะต่อ redirect ออกไปเว็บตัวเองได้ แล้ว token ก็หลุดไปด้วย (RFC 6749 §10.15) |
| **กลายเป็น XSS** | ถ้าค่าปลายทางถูกเอาไปใส่ใน `location.href` หรือ `<a href>` ฝั่งเบราว์เซอร์ ค่า `javascript:...` จะรันโค้ดบนหน้าเว็บเราได้ อย่าพึ่งให้เฟรมเวิร์กกันให้ ต้องตรวจเองด้วย |

ข้อ OAuth เกี่ยวกับ songtor โดยตรง ใน [backlog](../backlog.md) มีแผนย้ายไปใช้ Supabase Auth และอาจเพิ่ม social login ภายหลัง พอถึงตอนนั้นช่องโหว่นี้จะร้ายแรงขึ้นอีกขั้น

## 4. ทำไมเช็คแบบง่ายๆ ไม่พอ

ความผิดพลาดที่พบบ่อยที่สุดคือ **ตรวจด้วยกฎที่ไม่ตรงกับที่เบราว์เซอร์ตีความจริง** ตารางข้างล่างได้มาจากการรันสคริปต์จริง `browser→` คือ origin ที่ `new URL(ค่า, "https://songtor.app/login")` ให้ออกมา ซึ่งเป็น URL parser ตามมาตรฐาน WHATWG ตัวเดียวกับที่เบราว์เซอร์ใช้

| ค่า `next` | เบราว์เซอร์พาไปที่ | กฎที่พลาด |
|---|---|---|
| `/products/1` | songtor.app ✅ | ค่าปกติ |
| `//evil.com` | **evil.com** | `startsWith("/")` ผ่าน แต่ `//` แปลว่า "ใช้ protocol เดิม แล้วไปโดเมนนี้" (protocol-relative URL) |
| `/\evil.com` | **evil.com** | เบราว์เซอร์ถือว่า `\` เท่ากับ `/` ใน URL แบบ http/https |
| `\\evil.com` | **evil.com** | เหตุผลเดียวกับข้างบน |
| `/<tab>/evil.com` | **evil.com** | parser ลบ tab และขึ้นบรรทัดใหม่ทิ้งก่อนตีความ ค่านี้จึงกลายเป็น `//evil.com` |
| `␣//evil.com` (มีช่องว่างนำหน้า) | **evil.com** | parser ตัดช่องว่างหัวท้ายทิ้ง |
| `https://songtor.app.evil.com` | **songtor.app.evil.com** | `startsWith("https://songtor.app")` ผ่าน แต่นี่คือ subdomain ของ evil.com |
| `https://songtor.app@evil.com` | **evil.com** | ส่วนก่อน `@` คือ username ไม่ใช่โดเมน |
| `https://evil.com/?x=songtor.app` | **evil.com** | `includes("songtor.app")` ผ่าน |
| `javascript:alert(1)` | ไม่มี origin | ถ้าไปอยู่ใน href จะรันโค้ด |
| `/%2F/evil.com` | songtor.app ✅ | `%2F` ใน path ไม่ถือเป็นตัวคั่น เลยยังอยู่ในเว็บเรา |

ทุกบรรทัดที่ขึ้นว่า evil.com คือกฎที่คนเขียนคิดว่าปลอดภัยแล้ว แต่ **ตัวตรวจกับเบราว์เซอร์อ่าน URL คนละแบบ**

## 5. วิธีป้องกัน เรียงจากดีที่สุด

### ก. ไม่รับ URL จากผู้ใช้เลย

ส่งแค่ "รหัส" มา แล้วแปลงเป็น URL ฝั่งเซิร์ฟเวอร์

```ts
const DESTINATIONS = { chat: (id: string) => `/chat/${id}`, product: (id: string) => `/products/${id}` };
// ?next=chat&id=abc
```

วิธีนี้ปลอดภัยที่สุด เพราะผู้ใช้ไม่มีทางใส่ URL เองได้เลย ข้อเสียคือทุกครั้งที่มีปลายทางใหม่ต้องมาเพิ่มในรายการ

### ข. รับเฉพาะ path ภายในเว็บ ← songtor ใช้วิธีนี้

```ts
export function safeNextPath(raw: unknown): string {
  const value = Array.isArray(raw) ? raw[0] : raw;
  if (typeof value !== "string") return "/";
  if (!value.startsWith("/")) return "/";                                // ตัด URL เต็ม, javascript:, ช่องว่างนำหน้า
  if (value.startsWith("//") || value.startsWith("/\\")) return "/";     // ตัด protocol-relative
  if (/[ -]/.test(value)) return "/";                   // ตัด tab/newline ที่ parser จะลบทิ้ง
  return value;
}
```

ใช้หลัก **allowlist ไม่ใช่ blocklist** คือกำหนดว่าอะไร **ผ่านได้** ไม่ใช่ไล่จับว่าอะไรอันตราย อะไรที่ไม่ใช่ path ภายในเว็บจะตกไปหน้าแรกทั้งหมด

ถ้าเจอค่าแปลกๆ จะ **ปฏิเสธทิ้งเลย ไม่พยายามทำความสะอาด** เช่น ไม่ลบ tab ทิ้งแล้วใช้ค่าที่เหลือ เพราะโค้ดที่ทำความสะอาดมักมีช่องให้เล่นซ้อนเข้าไปได้อีก

### ค. แปลงเป็น URL ด้วย parser ตัวเดียวกับเบราว์เซอร์ แล้วเทียบ origin

```ts
export function safeNextPath(raw: string, origin: string): string {
  try {
    const url = new URL(raw, origin);
    if (url.origin !== origin) return "/";
    return url.pathname + url.search + url.hash;
  } catch {
    return "/";
  }
}
```

ข้อดีคือใช้ parser ตัวเดียวกับเบราว์เซอร์ จึงไม่มีปัญหา "ตีความคนละแบบ" แบบในตารางข้อ 4 ข้อเสียคือต้องรู้ `origin` ของเว็บตัวเอง ซึ่งพอมีทั้ง localhost, UAT และ PRD ก็ต้องดึงมาจาก config

### ง. Allowlist โดเมน

ใช้เมื่อ **จำเป็นต้อง** พาไปเว็บอื่นจริงๆ เช่นมีหลายโดเมนในเครือ ให้เทียบ `url.hostname` แบบ **ตรงกันทั้งคำ** กับรายการโดเมนที่อนุญาต ห้ามใช้ `endsWith` หรือ `includes`

### หลักที่ใช้ได้กับทุกวิธี

- **ตรวจที่จุดเดียวฝั่งเซิร์ฟเวอร์** ใน songtor [login/page.tsx](../../src/app/login/page.tsx) เรียก `safeNextPath` ก่อนส่งค่าให้ฟอร์ม ฝั่ง client จึงได้รับเฉพาะค่าที่ตรวจแล้ว
- **จุดไหนรับ URL ต้องผ่านฟังก์ชันเดียวกัน** ถ้าวันหนึ่งหน้า register ตรวจเอง แต่ใช้กฎไม่ตรงกับหน้า login ช่องโหว่ก็กลับมา
- **ถ้าจำเป็นต้องพาออกไปเว็บอื่น** ให้มีหน้าคั่นว่า "คุณกำลังออกจาก songtor ไปที่ ..." เพื่อให้คนเห็นปลายทางก่อนกดไปต่อ

## 6. จุดที่เกี่ยวข้องในโปรเจคนี้

แนวคิดที่ใช้ไล่หาช่องโหว่กลุ่มนี้คือ **source กับ sink**

- **source** = ข้อมูลที่ผู้ใช้ควบคุมได้ เช่น query string, form, header
- **sink** = จุดที่ข้อมูลไปก่อผล เช่น `router.push`, `redirect()`, `location.href`, `<a href>`

ช่องโหว่เกิดเมื่อมีเส้นทางจาก source ไปถึง sink โดยไม่ผ่านการตรวจ ผลที่ไล่ดู sink ทุกจุดในโปรเจค (ณ วันที่เขียน)

| Sink | ปลายทางมาจากไหน | ปลอดภัยไหม |
|---|---|---|
| `LoginForm.tsx` `router.push(next)` | `?next=` ← **ผู้ใช้คุมได้** | ✅ ผ่าน `safeNextPath` ใน page.tsx |
| `RegisterForm.tsx` `router.push(next)` | `?next=` ← **ผู้ใช้คุมได้** | ✅ ผ่าน `safeNextPath` ใน page.tsx |
| `BuyButton` / `ChatThread` `/orders/${id}` | id ที่เซิร์ฟเวอร์ส่งกลับมา | ✅ ขึ้นต้นด้วย path ที่กำหนดตายตัว |
| `SellForm` `/products/${id}` | id ที่เซิร์ฟเวอร์ส่งกลับมา | ✅ |
| `ProvinceFilter` `/?province=...` | ตัวเลือกใน select + `encodeURIComponent` | ✅ ขึ้นต้นด้วย `/?` ตายตัว |
| `products/[id]/edit` `redirect(/products/${id})` | route param | ✅ ขึ้นต้นด้วย path ตายตัว |
| ที่เหลือ | path คงที่ เช่น `/login`, `/admin` | ✅ |

กฎที่ได้จากตารางนี้: ถ้า **ส่วนต้นของ URL เป็นค่าคงที่ที่เราเขียนเอง** (`/orders/`, `/?`) ผู้ใช้เปลี่ยนโดเมนปลายทางไม่ได้ เพราะแก้ได้แค่ส่วนท้าย ช่องโหว่จะเกิดเมื่อ **ผู้ใช้คุม URL ได้ทั้งเส้นตั้งแต่ตัวอักษรแรก**

## 7. แบบฝึกหัด

1. **ลองดูว่าเบราว์เซอร์ตีความยังไง** เปิด DevTools (F12) ไปที่ Console แล้วพิมพ์
   ```js
   new URL("/\\evil.com", "https://songtor.app").href
   new URL("https://songtor.app@evil.com").hostname
   new URL("/\t/evil.com", "https://songtor.app").href
   ```
   ใน JavaScript ต้องพิมพ์ `\\` สองตัวถึงจะได้ backslash หนึ่งตัว

2. **Mutation test** เปิด [safeRedirect.ts](../../src/lib/safeRedirect.ts) แล้วลบ `|| value.startsWith("/\\")` ออก จากนั้นรัน
   ```bash
   npx vitest run src/lib/safeRedirect.test.ts
   ```
   ควรมีเทสต์แดงหนึ่งข้อ ลองทำแบบเดียวกันกับบรรทัดเช็คอักขระควบคุม เสร็จแล้วอย่าลืมใส่คืน

3. **เขียนแบบ ค.** ลองเขียน `safeNextPath` ใหม่ด้วย `new URL` แล้วรันเทสต์ชุดเดิม ถ้าผ่านทุกข้อ ให้คิดต่อว่าแบบไหนดีกว่ากันสำหรับ songtor และเพราะอะไร (ใบ้: `origin` ของ localhost, UAT และ PRD ไม่เหมือนกัน)

4. **หาเคสที่เทสต์ยังไม่ครอบ** ตารางข้อ 4 มีแถวไหนบ้างที่ยังไม่อยู่ใน [safeRedirect.test.ts](../../src/lib/safeRedirect.test.ts) ลองเพิ่มเข้าไป

## 8. อ่านต่อ

- **OWASP Cheat Sheet: Unvalidated Redirects and Forwards** อธิบายวิธีป้องกันพร้อมตัวอย่างหลายภาษา
- **CWE-601** คำจำกัดความทางการ พร้อมตัวอย่างช่องโหว่จริง
- **PortSwigger Web Security Academy** ค้นคำว่า "open redirection" มี lab ให้ลองโจมตีเว็บจำลองได้ฟรี
- **RFC 6749 §10.15 "Open Redirectors"** ส่วนที่ว่าด้วยความเสี่ยงของ open redirect ใน OAuth 2.0
- **RFC 9700 (OAuth 2.0 Security Best Current Practice)** แนวปฏิบัติด้านความปลอดภัยของ OAuth ฉบับปัจจุบัน
- **WHATWG URL Standard** สเปกของวิธีที่เบราว์เซอร์ parse URL เป็นที่มาของทุกแถวในตารางข้อ 4 อ่านยาก แต่ใช้เป็นแหล่งอ้างอิงสุดท้ายได้
